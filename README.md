# Popal 🎮

**Popal** — безкоштовна 3D-браузерна гра (PWA) про пригоду та власну базу: ловіть
істот кулями, збирайте ресурси, будуйте базу, а спіймані помічники добуватимуть
ресурси за вас. Гра працює просто в браузері телефона чи компʼютера:
**[popalgame.pl](https://popalgame.pl/)** · версія **Beta 0.2.2**

---

## Швидкий старт

Потрібен Node.js ≥ 18.

```bash
npm install        # залежності для розробки (eslint тощо)
npm start          # локальний сервер → http://localhost:5173
npm run check      # лінт + тести (те саме, що крутить CI)
npm test           # лише тести
npm run lint       # лише ESLint
npm run bump       # синхронізує версію кешу sw.js з package.json
```

Для локальної перевірки виконай `npm run check`, а для запуску гри — `npm start`.

Гра — статичний сайт **без кроку збірки**: правиш файли в `site/` → пушиш у
`main` → GitHub Actions сам задеплоїть на Firebase Hosting.

## Структура проєкту

```
├── site/                      # УСЯ гра — деплоїться як є
│   ├── index.html             # лендінг (опис, інструкції встановлення PWA)
│   ├── game.html              # ігровий shell: HUD, меню, підключення модулів
│   ├── sw.js                  # service worker (офлайн-кеш, мережа-перша)
│   ├── manifest.webmanifest   # маніфест PWA (fullscreen, landscape)
│   ├── firebase.json          # хостинг: no-cache для html/js/css
│   ├── three.min.js           # локальний three.js r128 + fallback на CDN
│   ├── src/styles/{game.css,premium.css}
│   ├── src/modules/*.js       # ігрові модулі (див. таблицю нижче)
│   ├── sounds/                # музика (день/ніч), SFX, голоси істот
│   └── img/                   # зображення істот, іконки
├── scripts/
│   ├── serve.mjs              # dev-сервер (npm start)
│   └── sw-version.mjs         # версіонування кешу sw.js (npm run bump)
├── tests/                     # тести (node --test)
├── eslint.config.mjs          # конфіг ESLint
└── .github/workflows/deploy.yml
```

## Архітектура гри

**Без бандлера й без ES-модулів.** `game.html` підключає `three.min.js`, потім
SDK Firebase (з CDN), потім модулі зі `src/modules/` у **суворому порядку**.
Модулі — класичні скрипти, що свідомо діляться глобальними змінними:

- ранній модуль щось оголошує (`R`, `sc`, `cam`, `P`, `pals`, `save`, `msg`…),
- пізніші це читають/музають; частина модулів загорнута в IIFE,
- доступ із «середини» до глобальних змінних іде через хелпер
  `GC('назва')` (обгортка над `eval`, кешує результат).

Звідси два головні правила розробки:

1. **Порядок `<script>` у game.html змінювати не можна** — він і є «граф залежностей».
2. Нова глобальна назва → допиши її в `PROJECT_GLOBALS` в `eslint.config.mjs`
   (інакше `no-undef` не зможе зловити твої майбутні друкарські помилки).

Тест `tests/globals.test.mjs` додатково стереже колізії: якщо два модулі
оголосять одну назву верхнього рівня, другий скрипт впаде з SyntaxError ще на
завантаженні — тест зловить це до деплою.

У v0.3.0 додано рівні Попал-центру з вимогами до рівня героя й матеріалів,
збереження вантажу працівників між завантаженнями, зміни трави та води,
палітру світу й точніше зіткнення камери з рельєфом. У v0.4.0 з'явився
перший ігровий зріз нової візуальної сцени: процедурно скіновані моделі героя
та Пухоклуба, дерева з картками листя, альфа-тестом і вітром, стежка до
кам'яної арки. У v0.5.0 герой отримав імпортовану 3D-модель GLB з ригом та
анімаціями; процедурна модель лишається резервним варіантом. Походження,
підготовку й поточні умови ліцензії моделі описано в
[`docs/hero-model.md`](docs/hero-model.md). Інші персонажі й оточення, а також
подальша візуальна робота залишаються в плані; якість не є рівнозначною
Palworld.

## Збереження прогресу

- Локально: `localStorage` (ключ `zi`); імʼя героя й гра доступні без входу,
  зокрема коли Firebase недоступний.
- Хмара: Firestore проєкту `popal-4da6b` (колекції `players`, `profiles`,
  `names`, `meta`) — для синхронізації між пристроями потрібен вхід через
  Google/пошту; найкращий прогрес можна відновити в профілі.

## Версіонування та кеш

Версія гри живе в **`package.json`**. Тести (`tests/version.test.mjs`) стежать,
що та сама версія стоїть у назві кешу `sw.js` і в стопці `index.html`.

Випуск нової версії:

```bash
# 1) підправ код
# 2) підбий версію в package.json (наприклад 0.3.1) і в стопці index.html
npm run bump      # оновить назву кешу у sw.js
npm run check     # переконайся, що все зелене
git commit && git push   # CI задеплоїть; перед деплоєм допише sha коміту
```

CI перед деплоєм виконує `node scripts/sw-version.mjs --sha $GITHUB_SHA`,
тож кожне вбудовування має свіжий кеш — клієнти не сидітимуть на старих файлах.

## Деплой

- Пуш у `main` → `deploy.yml`: перевірки → деплой папки `site/` на Firebase
  Hosting (канал `live`).
- Потрібні secrets репозиторію: `FIREBASE_SERVICE_ACCOUNT`.
- Не кладіть `.zip` у корінь репозиторію — CI свідомо падає з підказкою.

## Розробка: чого триматися

- Код свідомо мінімалістичний (короткі назви, щільні рядки) — ESLint тут
  перевіряє лише **коректність** (`no-undef`, `no-dupe-keys`, …), не стиль.
- `three.min.js` — вендорський файл, не редагується (у lint-і проігнорований).
- Після кожної зміни: `npm run check` + швидкий прогін `npm start` у браузері.
